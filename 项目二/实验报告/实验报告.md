# 面向液位控制站的 Modbus TCP 至 OPC UA 协议网关 —— 实验报告

## 1. 实验目的

在项目一（K10 液位控制站，Modbus TCP 从站）的基础上，实现一个运行于 PC 的协议网关：
将 K10 的 Modbus TCP 数据转换为 OPC UA 设备集成（DI）信息模型，允许第三方 OPC UA
Client（UaExpert）读取数据、修改参数和调用设备方法。

## 2. 软件系统架构

```
K10 (Modbus TCP 从站 :502)          PC 网关（本项目）               第三方 UA Client
┌─────────────────────┐   ┌───────────────────────────────┐   ┌──────────────┐
│ 输入寄存器 24 个    │◄──│ Modbus 轮询任务 (500ms)         │   │   UaExpert   │
│ 保持寄存器 26 个    │──►│  ├ AsyncModbusTcpClient 读全部  │◄──┤ browse/read  │
│ (项目一寄存器表)     │   │  ├ 解码 ABCD float32           │   │ write/method │
└─────────────────────┘   │  ├ 更新 UA 变量（双向转换）      │   └──────────────┘
                          │  └ UA 写/方法 → FC16 写回        │
                          │ OPC UA 服务器（asyncua 2.1）     │
                          │  ├ 官方 DI NodeSet（438 节点）   │
                          │  ├ TankType（DeviceType 子类型） │
                          │  ├ Tank1 实例：18 变量 + 6 方法  │
                          │  └ 诊断：ModbusConnected/        │
                          │     LastError/PollCount          │
                          └───────────────────────────────┘
```

**技术选型说明**：老师演示栈（open62541/C + nodeset_compiler）标注"仅供参考"。
本方案选 Python + asyncua 2.1：项目二官方要求提交 zip 排除 `.venv/__pycache__`
（Python 专属目录，说明 Python 实现被认可）；asyncua 原生加载官方 NodeSet XML
（免 nodeset_compiler 编译）；复用项目一的 pymodbus 生态与寄存器表。

## 3. 信息模型（DI 规范）

- 导入 OPC Foundation 官方 DI companion NodeSet（`nodesets/Opc.Ua.Di.NodeSet2.xml`）
- `TankType`：`DeviceType`（DI ns, ns;i=1002）的 HasSubtype 子类型
- DI 标准属性：SerialNumber / Manufacturer / Model
- 变量 18 个：Level/Error/ValveIn/FlowIn/FlowOut/Temperature（只读，输入寄存器映射）；
  Setpoint/ValveOut/Kp/Ki/Kd/PIDPeriod/Area/Height/QinMax/QoutMax/ExpN/Speed
  （可写，保持寄存器映射）
- 方法 6 个：SetSetpoint / SetValveOut / SaveParams / ClearIntegral / Start / Stop
- 诊断变量：ModbusConnected / LastError / PollCount

## 4. 双向转换

寄存器 uint16 对 ↔ 工程 float（ABCD 布局，与项目一固件/上位机完全一致）；
UA 写入越界 → 返回 `BadOutOfRange` 状态码并恢复原值，同时写入 LastError 诊断。

## 5. 开发过程（大模型辅助，重点章节）

按老师迭代思想 G1→G5，每步独立验证。本环节发现并解决 6 个技术问题：

| # | 问题 | 现象 | 定位与解决 |
|---|---|---|---|
| 1 | DI NodeSet 导入失败 | BadParentNodeIdInvalid | asyncua XML 导入器 strict 模式无法处理 DI 1.0 废弃参数节点断链 → strict_mode=False 导入 438 节点，DeviceType 层级完整 |
| 2 | 类型实例化"空壳" | Tank1 子节点数 = 0 | 实测发现 asyncua 的 add_object 不自动复制类型子节点 → 变量/方法在类型（建模声明）与实例（运行）双挂 |
| 3 | BadTypeMismatch 三连 | 轮询循环反复异常 | ① Variant(0, Boolean) 初值不是 bool ② Python int 写 UInt16/UInt32 不自动转换（显式 ua.Variant） ③ 状态码名应为 BadOutOfRange（无下划线）——通过异常回溯逐一定位 |
| 4 | 初始化竞态 | 开机把 0 写进设备 | UA 变量初值 0 ≠ Modbus 实际值，差分写回逻辑误判为客户端写入 → 首个成功轮询周期先回填不写回 |
| 5 | 写回竞态 | 方法 SetValveOut 无效 | 方法写 Modbus 后，差分逻辑把 UA 旧值又写回去 → 网关写 Modbus 后同步 UA 变量 |
| 6 | pymodbus 异步客户端限制 | no running event loop / 参数错误 | 客户端必须在事件循环内创建；read 的 count/device_id 是 keyword-only 参数 |

**方法论**：所有问题通过"最小复现 + 隔离测试"定位（如单独测试 add_object 的实例化行为、
给轮询循环加完整回溯日志），不靠猜。

## 6. 实验结果（验收对照）

| 验收项 | 结果 |
|---|---|
| Modbus 通讯：连接 K10 稳定读取 | ✅ 500ms 轮询，PollCount 持续递增；真机数据实时（液位/温度/流量） |
| OPC UA 服务：Client 能连接 | ✅ asyncua 客户端 + **UaExpert 实测**均连接成功 |
| DI 信息模型：TankType 基于 DeviceType | ✅ 程序断言 DeviceType 的 HasSubtype 子类型包含 TankType |
| Variable 浏览/读/写 | ✅ UaExpert 浏览 Tank1 全部变量；写 Setpoint → K10 实际响应 |
| Method 修改设定值 | ✅ SetSetpoint(300) → 真机液位从 250 开始爬升（实测 260.6mm 持续上升） |
| 数据转换 | ✅ 进出流量 0.849 L/min（与项目一稳态一致）；ABCD 布局全链路一致 |
| 状态诊断 | ✅ ModbusConnected 断线翻转 / LastError 记录越界拒绝 / PollCount |

**断线诊断测试**：断开 Modbus 从站 → ModbusConnected 变 False、LastError 记录连接异常；
恢复从站 → 自动重连、状态恢复 True（无需重启网关）。

## 7. 结论

网关全部验收项达成。技术选型（Python + asyncua）在开发效率上远优于 C 方案
（无编译步骤、XML 模型直接加载、与项目一 Python 生态无缝衔接），DI 信息模型
使用官方 NodeSet 保证规范符合性。asyncua 的 6 个特性坑均有据可查（本报告第 5 节），
为后续工业协议网关开发积累了可直接复用的经验。
