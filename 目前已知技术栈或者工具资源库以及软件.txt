目前从老师开发过程部分演示中提取到的所需技术栈或者开发工具与资源库，仅供参考，不一定需要完全照做：

## 一、开发平台 / 工具

1. **VSCode**：代码编辑器，用来写 C 代码、看 CMakeLists、查看 xml、调试
2. **CMake**：构建工具，用来配置、生成编译脚本
3. **make**：编译工具，编译 open62541 以及你的服务端程序
4. **UaExpert**：OPC UA 客户端调试工具（可视化浏览地址空间、读变量、调用方法、测试服务器）
5. **Git**：版本控制，拉取源码、子模块、同步仓库（`.gitmodules`）

## 二、核心技术栈

1. **OPC UA**：工业通信协议，整套项目的核心
2. **C 语言**：open62541 原生开发语言
3. **NodeSet（XML 节点集）**：OPC UA 信息模型描述文件，用来定义设备、变量、方法
4. **nodeset_compiler**：配套编译工具，把 XML 模型 → 转换成 C 源码（**重点**：不能直接加载 xml）
5. C/S 架构、Subscription/MonitoredItem 订阅机制（OPC UA 服务模型）

## 三、资源库 / 仓库

1. **open62541**：核心开源 OPC UA SDK（C 语言实现，用来开发 OPC UA 服务器 / 客户端）
2. **UA-Nodeset**：OPC UA 标准节点集仓库（存放 DI、ISA95 等标准设备模型 xml）
   - 原版：GitHub；国内镜像：Gitee（老师说国内拉取更快）
3. Git 子模块（submodule）：用来在工程里自动关联拉取上面的 nodeset 资源

## 四、配套规范（信息模型）

- **DI 规范（Device Information）**：设备信息标准模型，液位控制器就属于设备，可以基于 DI 建模

## 五、整套链路一句话串起来

Git 拉取 open62541 + UA-Nodeset（xml 模型）→ CMake+make 编译，nodeset_compiler 转 xml 为 C 代码 → VSCode 写业务逻辑（液位控制）→ 编译运行 OPC UA 服务器 → UaExpert 连接调试、测试读写和方法调用

agent给出的非瀑布式开发流程（也仅供参考，具体工作流还需要自行根据实际情况调整，由于是课程项目，所以还需要附带输出开发过程的实验报告，实验报告的要求后续会给出）：

瀑布是：**全部代码、全部模型一次性写完，最后一次性编译、联调**，一旦模型写错、逻辑错，很难定位，工业项目很容易崩。
迭代 + 模块化：**拆成独立小模块，做完一块、验证一块，再往下走**，每一步都能用 UaExpert 验证，前面没问题再做后面。

## 液位 OPC UA 项目 迭代开发流程（分阶段，每阶段可单独测试）

> 
> 前提：环境已经装好（Git、CMake、open62541、UaExpert、nodeset_compiler）

### 迭代 1：基础环境与最简 OPC UA 服务器（只跑通通信，无液位业务）

目标：先保证服务器能正常启动、客户端能连上

1. 拉取 open62541 源码，编译基础示例
2. 写一个最小服务端，只建一个简单变量（比如随便一个浮点值）
3. 运行服务器，**UaExpert 连接、浏览节点、读写这个变量**
✅ 验收标准：能连上、能读写，通信链路没问题
👉 这一步只验证协议栈，不碰液位、不碰 DI 模型

### 迭代 2：信息模型模块（NodeSet XML 建模，独立验证模型）

目标：搭液位设备的地址空间，定义设备、液位变量、控制方法

1. 引用 DI 标准模型（UA-Nodeset 里的 DI），在 XML 里自定义：液位对象、液位值变量、启停控制方法
2. 用 `nodeset_compiler` 把 XML → 生成 C 代码
3. 把生成的模型代码加到工程，编译
4. 启动服务，UaExpert 查看地址空间：检查节点结构、变量、方法是否和你设计的一致
✅ 验收标准：模型结构正确，节点全部出现
👉 这一步只管**模型长什么样**，不写控制逻辑，模型和业务解耦

### 迭代 3：数据采集模块（模拟液位采集，独立模块）

目标：给液位变量灌入数据，先模拟，后面再对接真实传感器

1. 写独立采集函数：模拟液位值周期性更新（比如 0~100）
2. 绑定到 OPC UA 变量：周期性刷新节点的值
3. 启动服务，UaExpert 看变量是否自动刷新
✅ 验收标准：变量自动更新，订阅（Subscription）能收到变化通知
👉 只负责读数据，不做 PID、不做阀门控制

### 迭代 4：控制方法模块（OPC UA Method，独立调试）

目标：实现远程控制接口，通过 UaExpert 调用方法

1. 实现控制回调函数：启动、停止、设置液位阈值
2. 绑定到刚才 XML 定义的 Method 节点
3. UaExpert 直接调用这个方法，看服务器是否执行回调、打印日志
✅ 验收标准：调用方法有响应，参数收发正常
👉 只做接口响应，暂时不闭环控制

### 迭代 5：闭环控制业务模块（液位调节逻辑）

目标：把采集到的液位 + 控制接口结合，做闭环（比如 PID）

1. 写控制逻辑：根据当前液位和设定值，输出阀门开关量
2. 和前面采集模块、方法模块对接
3. 运行，UaExpert 一边看液位，一边调用设置阈值，观察自动调节
✅ 验收标准：可以自动维持液位

### 迭代 6：整合、异常与容错模块（健壮性）

1. 增加异常处理：断连、非法参数、液位超限报警节点
2. 整体联调、压力测试订阅、反复调用方法
3. 最后再考虑对接真实硬件（替换模拟采集）

## 核心要点（老师强调的模块化迭代思想）

1. **模块之间低耦合**
   - 通信模块（open62541 服务）、信息模型（XML）、采集模块、控制逻辑、远程方法，互相分开。
   - 模型改了，不用重写控制；控制逻辑改了，不用重新改 XML。
2. **每一次迭代都有可验证的产物**
每一轮做完，都能用 UaExpert 做黑盒测试，**尽早发现问题**，而不是等到全部写完才调。
3. 顺序原则：**先通通信 → 再搭模型 → 再跑数据 → 再加控制逻辑**
4. 对比瀑布：
   - 瀑布：XML 建模 + 采集 + 控制 + 方法全部写完 → 编译 → 一次性调试，错了不知道是模型错还是逻辑错
   - 迭代：一小块做完，验证通过，再下一块，问题范围被锁死
